# Agent 研讨室 · CLI 代理注入与检测改造 —— 探索结论

> 记录时间：2026-07-04
> 状态：探索/验证已完成，方案骨架已定，**尚未进入 OpenSpec propose、未改任何代码**
> 用途：留待后续正式开 change 处理

---

## 1. 一句话结论

研讨室里 claude 调不通的**首要根因是「没注入代理」**：Dock 启动的 Electron 主进程不继承终端 shell 的代理环境变量，spawn 出的 claude 直连官方 API 连不上。**次要问题**是检测逻辑里 `claude auth status` 命令在 claude 2.x 已不存在，登录态判断恒为 false（隐藏 bug）。两者需一并处理。

---

## 2. 关键根因

### 根因一（首要）：spawn 未注入代理

- `runner.js` 的 `spawn(command, args, { cwd, shell:false, detached:true })` **没有传 `env`** → 子进程继承的是 Electron 主进程环境。
- Dock 启动的 OneApp 拿的是 launchd 最小环境，**不含**用户 `~/.zshrc` 里 export 的 `http_proxy`/`https_proxy`。
- 结果：研讨室里的 claude 直连 `api.anthropic.com` 连不上（需经本地代理才能访问）。

### 根因二（次要，隐藏 bug）：检测命令已失效

- `detection.js:51` 用 `claude auth status` 解析 JSON 的 `loggedIn`。
- 实测（claude **2.1.6**）：`claude auth status` → 退出码 1、`error: unknown command 'auth'`。
- `auth` 子命令在当前 claude 已不存在 → `pexec` reject → 进 catch → **`loggedIn` 恒为 false**。
- 影响（强推断、待确认 UI 消费链）：claude 卡片可能一直显示未登录、无法被选为研讨 agent/主持。

> 优先级关系：**即使修好检测 bug，不注入代理 claude 照样连不上**；反过来，检测的实调也**必须带代理**才准。所以代理是第一位、检测是第二位。

## 3. 实测证据

| 测试 | 命令要点 | 结果 | 结论 |
|---|---|---|---|
| curl 直连官方（无代理） | `curl https://api.anthropic.com/` | 15s 超时、`http_code=000` | 直连不通 |
| claude 最小实调（无代理） | `claude --print`，unset 全部代理 | **38s 超时、`Connection error`** | 复现研讨室现状 |
| curl 经代理连官方 | `curl -x http://127.0.0.1:7897 ...` | **401、1.08s** | 代理到官方**完全通**（401 只是没带 key） |
| claude（只设大写 `HTTPS_PROXY`） | `HTTPS_PROXY=... claude --print` | **rc=0、输出 `pong`** | claude 能走代理 |
| claude（大写 `HTTP_PROXY`+`HTTPS_PROXY`） | 拟采用组合 | **rc=0、`pong`（稳定）** | ✅ 方案组合可用 |
| claude（再加 `ALL_PROXY`） | 追加 all_proxy | rc=0、`pong` | 加 all_proxy 也 OK |
| `claude auth status` | 检测用的命令 | rc=1、`unknown command 'auth'` | 命令已失效 |

- claude 版本：**2.1.6**，路径 `~/.nvm/versions/node/v20.19.4/bin/claude`
- 本地代理：`http://127.0.0.1:7897`（探测端口 OPEN）

### 一个未决小疑点（低优先级，方案已规避）

首次「带全套 6 个代理变量（含小写 + all_proxy）」时出现过一次 **0s 立即失败**，但后续**未能复现**（加 `ALL_PROXY` 也成功）。判断为偶发（紧跟无代理 38s 超时之后的瞬时状态），**不是 `all_proxy` 的锅**。方案采用大写 `HTTP_PROXY`/`HTTPS_PROXY`，C/D/E 三次稳定成功，不受此影响。

## 4. 关于 `cc` / `claude-start.sh` 的澄清（纠正早期误判）

重读 `~/ai-workspace/envBuild/claude-start.sh` 真实内容（53 行）：

- 做的事：设**代理**(`127.0.0.1:7897`) + **时区**(America/Los_Angeles) + **语言**(en_US.UTF-8) + **环境漂移检测**（curl ipinfo.io 比对 baseline，变化则 `read -p` 交互确认）→ 末尾 `claude "$@"`。
- **不含** base_url / token / 自定义 provider —— claude 走的是官方 API，仅经本地代理。
- **不能直接拿来 spawn**：脚本含 `curl`（最多 5s 延迟）+ `read -p` 交互询问，非交互场景会读走 stdin 的 prompt、卡住。
- `cc-skip` = `cc` + `--dangerously-skip-permissions`，**会摧毁研讨室只读铁律，绝不可用于研讨室**。

> 早期我误以为脚本里有 `ANTHROPIC_*` 自定义 provider（base_url/token）——那来自另一个文件 `~/.claude/settings-backup.json`（**备份/历史配置**），与启动脚本、与当前需求无关。已纠正。

## 5. 方案骨架（待 propose）

**定义**：让研讨室的 CLI 调用（**检测实调 + 正式研讨都算**）注入一组用户可配的环境变量，首要是代理；并把检测从失效的 `auth status` 改成「注入 env 后的最小实调看退出码」。

一个改造同时解决三件事：① claude/codex 在研讨室连得上官方 API；② 顺手修 `auth status` 检测 bug；③ 对 codex 同样生效（它连 OpenAI 一样要代理）。

### 改动落点

| 模块 | 改动 |
|---|---|
| `electron/agentWorkshop/runner.js` | `spawn` options 加 `env: { ...process.env, ...injectedEnv }` —— 核心一行 |
| `electron/agentWorkshop/detection.js` | 探测实调带上 `injectedEnv`；登录态判断从 `auth status` 改为**带代理的最小实调**看退出码 |
| `electron/agentWorkshop/ipc.js` | 注入配置读写；把 `injectedEnv` 传给 detection 与 orchestrator 的 invoke |
| `src/renderer/utils/agentWorkshopHelper.js` | 注入配置的数据结构 + 校验（纯逻辑、可单测） |
| `src/renderer/components/AgentWorkshopTab.vue` | 左栏加「网络/环境」配置区 |
| electron-store | 新增 `injectedEnv`（或 `proxyConfig`）持久化项 |

**硬约束**：检测与正式调用**共享同一份注入 env**，否则会出现「检测说连不上、其实是检测自己没走代理」的假象。

### 检测分层（替换死掉的 auth status）

- **L1 装了吗**：`command -v claude` + `--version`（免费/快）
- **L2 配了吗**：读注入配置/settings（免费/快）
- **L3 能用吗**：**带代理**的最小实调（`echo hi | claude --print`，看退出码），做成「测试连接」按需触发，别每次自动烧 token

### 代理注入的技术要点

- 注入**大写** `HTTP_PROXY` / `HTTPS_PROXY`（实测稳定）
- 代理地址是**非敏感信息** → OneApp 存它不背 token 保管的安全责任
- env 注入碰不到 argv → **只读铁律不受影响**（plan 模式 + 只读工具白名单照常）
