## Context

`DiffTab.vue` 当前使用 `showDiff` 在双栏输入区与只读差异结果之间切换。点击“对比”后输入组件被卸载，结果态仍显示“对比”主按钮，却没有返回编辑的入口；“清空”则会同时丢弃两侧文本。组件还通过 `watch([textA, textB])` 在结果态自动重新计算，但结果态无法直接输入，该监听主要服务于加载文件和交换等程序化变更，状态意图不清晰。

现有 `diffTextSplit` 使用行级 LCS，时间和空间复杂度均随两侧行数乘积增长。本次是小型 UX 修复，应复用现有编辑器和差异算法，不将范围扩大到实时 Merge Editor 或算法重写。

## Goals / Non-Goals

**Goals:**

- 让用户从结果态返回输入态时保留文本 A 和文本 B。
- 允许用户只清空一侧内容，并立即在该侧继续输入。
- 保证结果态展示的差异始终对应当前源文本。
- 保留现有并排/统一视图、摘要、文件加载、交换和同步滚动行为。
- 使用小范围、无新增依赖的状态与模板调整完成修复。

**Non-Goals:**

- 不在差异高亮结果中直接编辑文本。
- 不引入 CodeMirror Merge Editor 或其他编辑器依赖。
- 不改变 `diffHelper.js` 的差异语义、统计规则或性能特征。
- 不新增文件夹对比、差异合并或逐项接受/拒绝功能。

## Decisions

### 1. 保留输入态与结果态分离，并让状态可逆

继续使用 `showDiff` 作为输入态/结果态的单一状态来源。输入态的主操作显示“对比”；结果态的主操作改为“编辑内容”。“编辑内容”只切换状态，不清空 `textA`、`textB`，因此用户可以修改任意一侧后再次显式对比。

选择该方案是因为它符合现有工具页面结构与 `tool-surface-refresh` 对输入和结果清晰区分的要求，也避免同屏放置四个面板。备选的 Merge Editor 能在高亮中编辑，但会引入新的组件、主题适配和大文本性能问题，不符合本次小修复范围。

### 2. 单侧清空放在对应输入面板标题栏

文本 A、文本 B 的输入面板标题栏分别提供“清空此侧”操作。操作只更新目标 ref，并通过 `nextTick` 聚焦对应 `EditorWithLineNumbers` 已暴露的 `textareaRef`；另一侧文本保持不变。“清空全部”继续位于工具栏并重置两侧内容与结果状态。

将操作放在面板内能明确作用范围，避免在顶部工具栏继续增加“清空 A”“清空 B”等并列按钮。

### 3. 差异计算改为显式触发

移除文本 ref 上的自动 `watch`。用户编辑内容后只在点击“对比”时计算结果；结果态下加载文件或交换文本时，由对应操作在状态更新完成后显式调用同一个 `compare()`，确保只计算一次且结果不会过期。

加载文件保持当前结果态的即时重新对比体验；用户若要先检查或修改新文件内容，可以使用“编辑内容”进入输入态。在输入态加载文件只更新输入，不提前生成结果。

### 4. 结果数据继续作为派生状态集中刷新

`compare()` 继续集中更新 `diffSplitResult`、`diffUnifiedResult`、`stats` 和 `showDiff`。所有进入或刷新结果态的路径均调用该函数，避免部分路径只更新源文本却保留旧结果。切换并排/统一视图只改变展示模式，不重复计算。

## Risks / Trade-offs

- [Risk] 返回输入态后，结果不会随键入实时变化，用户可能认为旧结果仍有效 → 输入态隐藏摘要和结果，并将主按钮明确显示为“对比”。
- [Risk] 新增程序化修改源文本的路径时可能忘记刷新结果 → 将结果刷新集中在 `compare()`，并为加载和交换路径补充回归验证。
- [Risk] 清空后立即聚焦可能早于 DOM 更新 → 使用 `nextTick`，并在组件引用存在时再调用 `focus()`。
- [Trade-off] 结果态仍不可直接编辑 → 以低复杂度换取清晰状态和现有大文本性能边界；直接编辑留作独立的 Merge Editor 需求。

## Migration Plan

1. 在新修复分支调整 `DiffTab.vue` 的上下文主按钮、面板操作和显式状态转换。
2. 运行现有 Diff helper 测试、完整单元测试与生产构建，并手动验证输入态/结果态往返和窄窗口布局。
3. 若出现回归，可回退单个组件改动；不涉及存储迁移、配置迁移或数据兼容处理。

无。后续若要在差异高亮中直接编辑，应作为独立 change 评估 Merge Editor 和大文本性能策略。
